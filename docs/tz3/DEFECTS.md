# Дефекты и блокеры ТЗ №3

## Порядок обработки во время живой приёмки

Во время первого полного живого прохода дефекты только фиксируются с воспроизведением, видимым результатом и приростом журналов. Немедленные продуктовые исправления не выполняются. После регистрации проблема не останавливает независимые сценарии.

Исправления выполняются одним подготовленным пакетом после завершения всех доступных проверок. Затем каждый дефект и весь затронутый бизнес-путь проходят повторную живую проверку. Исключение для аварийного исправления допускается только по отдельному решению владельца, если приложение невозможно безопасно запустить и никакой другой сценарий проверить нельзя.

3. Реализованы нормализация, опечатки, сокращения, дедупликация и Top-3.
4. Созданы автоматические отрицательные и контрактные тесты.
5. Создан эталон минимум 2 000 адресов / 10 000 запросов.
6. Выполнены метрики и живые проверки приоритетных регионов.

## Подтверждённые дефекты

### JF3-DEFECT-001 — GitHub Release невозможно было скачать

| Поле | Значение |
|---|---|
| GitHub | https://github.com/KAPCTEH/21.08reliz/issues/25 |
| Обнаружено | JF3-S0018 |
| Исправлено | `bdce184` |
| Source status | FIXED / PASS |
| Live status | NOT TESTED |

Причина: загрузчик отклонял любой HTTP redirect, тогда как GitHub Release Assets официально может возвращать `302` на фактическое хранилище.

Исправление: разрешено не более трёх переходов только между явно разрешёнными HTTPS-доменами. Размер и SHA-256 по-прежнему обязательны. Переход на посторонний домен отклоняется тестом.

Живое обновление реального установленного приложения ещё не выполнено, поэтому Issue закрывать рано.

### JF3-DEFECT-002 — Авторизация владельца не сохраняется после переустановки

| Поле | Значение |
|---|---|
| Тип | Reinstall / protected-session defect |
| Приоритет | P1 до update/reinstall acceptance |
| Обнаружено | JF3-S0034 |
| Состояние | OPEN |
| Source status | CONFIRMED |
| Live status | CONFIRMED |

Подтверждённые факты:

- предыдущий RC после регистрации владельца запускался с `authorized=true`;
- пользователь удалил прежнюю установку, но AppData приложения сохранился и был отдельно скопирован перед новой установкой;
- актуальная сборка установлена под тем же пользователем Windows и совпала с CI-манифестом по SHA-256;
- при первом запуске новая сборка записала `cloud auth state rejected` и сообщение о повреждённом ключе или другом пользователе Windows, затем открыла экран авторизации;
- после отклонения сессии `native-secrets.json` стал меньше и изменил SHA-256; содержимое и значения секретов не открывались;
- бизнес-данные на этом шаге не изменялись, новая компания не создавалась.

Подтверждённая причина необратимой потери сессии в исходниках:

- `readNativeSecret()` перехватывает любое исключение `safeStorage.decryptString()` и уничтожает исходный код ошибки (`source/application/main.js`, строки 820–826);
- `readCloudAuthState()` затем на любое такое исключение безусловно удаляет `licenseCloudAuthV1` (`source/application/main.js`, строки 974–989);
- поэтому даже временная ошибка Windows DPAPI превращается в постоянный выход из аккаунта и уменьшение файла защищённых секретов;
- сам установщик и Update Helper защищённый профиль пользователя не удаляют. Предыдущий RC и текущая сборка используют одинаковые `main.js`, Electron 43.3.0 и installer-код, поэтому несовместимость формата между этими сборками не подтверждена;
- первоначальную причину отказа DPAPI доказать уже нельзя: код скрыл HRESULT, а затем удалил исходный шифротекст. Возможны повреждение шифротекста или несовпадение реального DPAPI-контекста.

Безопасный временный обход: войти по коду существующей компании, логину и паролю. Повторно активировать лицензию и создавать новую компанию нельзя.

Условие закрытия:

1. Воспроизвести переход build A → build B через переустановку и через Update Helper в изолированном профиле.
2. Присвоить сбою расшифровки отдельный код `NATIVE_SECRET_DECRYPT_FAILED`, сохранить исходную причину в безопасном журнале без значений секретов и не удалять шифротекст при временном сбое DPAPI.
3. Удалять сессию только при доказанно невалидном формате или auth-контексте; при временной недоступности хранилища корректно запросить обычный повторный вход без ложного сообщения о повреждении ключа.
4. Добавить автоматический regression test и повторить живую проверку под тем же Windows-пользователем.

Обязательный regression test: сохранить auth-сессию, заставить mock `decryptString()` один раз выбросить исключение, получить безопасный `null`, подтвердить неизменность байтов и SHA-256 хранилища, восстановить decrypt и прочитать ту же сессию без повторного входа. Дополнительно выполнить Windows acceptance `build A → uninstall keep-data → build B` и `build A → Update Helper → build B` под тем же SID.

### JF3-BLOCKER-003 — Обычные изменения полностью заблокированы без VPS

| Поле | Значение |
|---|---|
| Тип | Architecture / offline acceptance blocker |
| Приоритет | P1 до финального выпуска |
| Обнаружено | Живое сохранение первого синтетического заказа |
| Состояние | OPEN |
| Source status | CONFIRMED |
| Live status | CONFIRMED |

Подтверждённое поведение: в full-редакции guard `commitEntityMutation()` возвращает `false` до локальной мутации, если сессия offline, у компании отсутствует `data_service` или недоступен `regVps.syncEntities`. Поэтому обычный заказ не попадает даже в локальное хранилище, а пользователь получает сообщение о необходимости рабочего VPS.

Блокировка намеренно закреплена source-contract тестом, но противоречит интерфейсу и ТЗ №3: встроенная справка обещает продолжение работы с локальной базой и фоновое восстановление связи; живой acceptance требует создания допустимых локальных изменений без сети.

Условие закрытия:

1. Ввести классификацию `LOCAL_DURABLE`, `SERVER_CONFIRMED`, `CRITICAL_FAIL_CLOSED`.
2. Для обычных изменений реализовать durable outbox с `command_id`, scope, base version, состояниями и повторной отправкой.
3. Не уничтожать локально сохранённое намерение при server-wins bootstrap; конфликт показывать явно.
4. Оставить fail-closed только для критических общих переходов состояния.
5. Выполнить полную матрицу [`LOCAL-FIRST-CONNECTIVITY-ACCEPTANCE.md`](LOCAL-FIRST-CONNECTIVITY-ACCEPTANCE.md) до и после подключения VPS/Telegram.

### JF3-RISK-002 — Общие тестовые VPS/D1 могут содержать legacy-схемы и данные

| Поле | Значение |
|---|---|
| Тип | Multi-tenant migration / data isolation risk |
| Приоритет | P1 до production onboarding |
| Состояние | OPEN RISK, LIVE INVENTORY NOT RUN |
| Source status | PARTIAL FOUNDATIONS CONFIRMED |

В текущем коде присутствуют schema migrations, PostgreSQL RLS, company/warehouse/environment scope и Telegram D1 migrations. Однако общие тестовые базы ещё не инвентаризированы на старые schema versions, orphan rows, legacy wildcard Telegram state и незавершённые операции. Поэтому наличие фактического конфликта пока не объявляется доказанным дефектом.

Условие закрытия: выполнить inventory без секретов, сохранить backup, применить и повторить идемпотентные миграции, проверить legacy quarantine, смешанные версии клиентов, cross-tenant negative tests и матрицу [`MULTI-TENANT-DATA-MIGRATION-SPEC.md`](MULTI-TENANT-DATA-MIGRATION-SPEC.md).
