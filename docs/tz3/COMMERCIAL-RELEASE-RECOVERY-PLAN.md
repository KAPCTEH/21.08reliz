# План восстановления коммерческого релиза JustFun

Дата: 28 августа 2026 года.

## 1. Исходная точка

- Переданный установщик 7.8.4 не прошёл живую приёмку владельца и не является готовым релизом.
- В реестре 61 блокер/дефект, 50 из них не закрыты доказательством установленной версии.
- Среди незакрытых позиций: 7 уровня P0, 27 уровня P1, 13 уровня P2 и 2 уровня P3; одна запись не имеет приоритета.
- Часть P0/P1 имеет исправление исходников, но не имеет обязательного живого повторного теста. Это не считается закрытием.
- Полный пользовательский проход не завершён, поэтому текущий список дефектов не является окончательным.

## 2. Разделение ответственности

### Codex обязан

1. Воспроизводить и исправлять дефекты в единственном каноническом репозитории.
2. Самостоятельно проверять исходники, установленную программу, журналы, VPS, Telegram и сохранённые данные.
3. Создать автоматизированный сценарий реальной приёмки, а не ограничиваться unit/source-тестами.
4. Проверять точный установщик с зафиксированными commit, build ID и SHA-256.
5. Предоставлять доказательства каждого обязательного сценария и честный список непроверенного.
6. Не использовать слова `готово`, `релиз` и `GO`, пока все обязательные условия не выполнены.

### Владелец обязан только

1. Принимать решения о бизнес-поведении, когда требования неоднозначны.
2. Не передавать секреты в чат и самостоятельно подтверждать только неизбежные операции входа/2FA.
3. В конце выполнить короткую контрольную приёмку ключевых действий. Владелец не должен вручную проверять всю программу.

## 3. Порядок исправления

### Пакет A — фундаментальные P0

1. Сессия VPS после подключения, outbox и серверное подтверждение операций.
2. Вход приглашённого сотрудника, назначение склада и запрет owner-only миграции для обычного пользователя.
3. Серверный контракт приглашений и совпадение клиента с развёрнутым Worker.
4. Согласованность версии приложения, build identity и заголовка окна.
5. Обновление, health confirmation и автоматический откат точной сборки.

### Пакет B — бизнес-функции P0/P1

1. Доставка и самовывоз от создания до завершения.
2. Резерв, списание, оплата, архив и повторное чтение после перезапуска.
3. Поиск адреса, координаты, маршрут и стоимость доставки.
4. Права владельца и сотрудника, несколько складов, второй профиль/ПК.
5. Offline, reconnect, повтор команды, конфликт версий и отсутствие двойных операций.
6. Резервная копия и восстановление.

### Пакет C — Telegram и UX

1. Понятные сообщения склада и водителя.
2. Все кнопки и переходы статусов Telegram.
3. Компактная форма товаров, удаление лишних блоков и текстов.
4. Масштабы Windows 100/125/150 процентов, клавиатура, длинные значения и печать/PDF.

P2/P3, не влияющие на безопасность и данные, выполняются только после закрытия P0/P1.

## 4. Обязательное доказательство каждого исправления

Для каждого дефекта нужны одновременно:

1. Воспроизведение ошибки до изменения.
2. Точная причина в цепочке UI → IPC/API → сервер/локальное хранилище → повторное чтение.
3. Минимальное исправление без обходного сценария.
4. Автоматический положительный и отрицательный тест.
5. Живой повтор на установленной точной сборке.
6. Скриншот результата и безопасный фрагмент журнала с correlation ID.
7. Для данных — сравнение состояния до/после и после перезапуска.

Одних зелёных тестов исходников недостаточно.

## 5. Контроль расхода лимитов и диска

- Не выполнять новые общие аудиты уже исследованного кода.
- Не собирать установщик после каждого исправления.
- Исправлять пакетами: фундамент → бизнес → UX.
- Между пакетами запускать только относящиеся к изменениям тесты.
- Полную матрицу запускать один раз перед единственной релизной сборкой.
- Старые сборки и временные worktree удалить только после отдельного подтверждения владельца.
- Сохранить канонический Git-репозиторий, рабочие данные, резервную копию, текущие журналы и финальный evidence-пакет.

## 6. Коммерческий release-gate

Статус `GO` разрешён только при одновременном выполнении всех условий:

1. Незакрытых P0 и P1 нет.
2. Чистая установка и обновление существующей версии прошли.
3. Владелец и приглашённый сотрудник работают только со своими складами.
4. Доставка и самовывоз полностью проходят с оплатой, резервом и списанием.
5. VPS/outbox, offline/reconnect и конфликт проверены без потери и дублирования данных.
6. Адрес, маршрут и Telegram прошли живой сценарий.
7. Резервная копия, восстановление и подписанный откат доказаны.
8. После нескольких штатных перезапусков состояние совпадает с сервером и локальной базой.
9. Финальный установщик имеет зафиксированные commit, SHA-256 и полный отчёт приёмки.
10. Владелец выполняет только короткую финальную проверку основных действий и принимает результат.

До выполнения этих условий программа остаётся тестовой сборкой и не должна продаваться.

## 7. Как владелец контролирует Codex

- Каждое утверждение должно иметь ссылку на файл, журнал, скриншот или серверный ответ.
- `SOURCE FIXED` не равно `LIVE PASS`.
- `TEST PASS` не равно `RELEASE GO`.
- Сборка не принимается без совпадения commit/build ID/SHA-256.
- Любая неизвестная или непроверенная часть явно остаётся открытой.
- Один критический FAIL автоматически возвращает статус `NO-GO`.
