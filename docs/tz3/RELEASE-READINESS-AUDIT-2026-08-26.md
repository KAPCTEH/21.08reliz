## 5. Новые и актуальные критические выводы

### 5.1. Недетерминированный local-first gate

Во время подготовки staging-bootstrap тест

```text
node tests/runtime-smoke.mjs source/application/web local-first-offline
```

с `JF_TEST_EDITION=full` дважды завершился ошибкой. После локального `persistOrders()` тестовый заказ исчезал при server bootstrap:

- `baselineLocalPresent=false`;
- `baselineServerPresent=false`;
- `deleteResult=false`;
- pending outbox отсутствовал;
- `restartPreserved=false`.

Повтор на основном worktree с теми же исходниками прошёл. Сравнение доказало точное совпадение SHA-256 двух ключевых файлов в обоих worktree:

- `110-desktop-platform-v750.js`: `95291785...a37a`;
- `runtime-smoke.mjs`: `01308b02...0674`.

Зависимость `jsdom` также одинакова: 26.1.0.

Наиболее вероятный причинный механизм виден в порядке таймеров:

- UI объявляется готовым раньше полного entity bootstrap;
- `installAutomaticCloudSync()` планирует bootstrap через 250 мс;
- обычный `persistOrders()` планирует background upload через 150 мс от момента изменения;
- при одном порядке выполнения локальное изменение успевает попасть в outbox и на сервер;
- при другом порядке server snapshot заменяет локальный snapshot раньше фиксации команды.

Честная классификация:

- **подтверждено:** релизный тест недетерминирован и gate нельзя считать надёжным;
- **подтверждено исходниками:** таймеры допускают окно конкуренции между готовностью UI, bootstrap и захватом локального изменения;
- **ещё не доказано трассировкой:** что именно этот порядок таймеров был непосредственной причиной каждого из двух упавших запусков;
- **не подтверждено живым приложением:** фактическая потеря пользовательского заказа на установленном ПК не воспроизведена;
- **релизное решение:** считать P0-блокером до детерминированного исправления и многократного PASS.

Сначала нужна узкая event/timer trace, которая докажет точный порядок неудачного запуска. Нельзя просто увеличить ожидание теста: это может скрыть реальное окно конкуренции. Если гипотеза подтвердится, требуется атомарно защищать изменения во время bootstrap либо не объявлять рабочую поверхность готовой до восстановления server snapshot и local outbox.

### 5.2. Publication verifier доверяет данным из подписанного каталога

Подпись доказывает, кто создал каталог, но не доказывает, что автор не ошибся. Текущий publication verifier принимает список разрешённых payload/release-notes hosts и набор contracts из самого каталога, а не сверяет их с каноническими:

- `source/application/update/policy.json`;
- `source/application/release.json`.

Отрицательная проверка показала, что workflow способен принять подписанный stable-каталог с посторонним host и вымышленным контрактом. Клиент затем отвергнет такой каталог, но production KV уже будет опубликован.

Это release-safety blocker. Перед stable workflow обязан сверять:

- payload host и redirect hosts с policy allowlist;
- release-notes host с policy;
- required contracts с текущим release contract;
- minimum supported version, product ID, channel и архитектуру с canonical source.

Дополнительное ограничение: history key защищён проверками workflow, но не является физически неизменяемым хранилищем. Cloudflare token с правом KV Edit технически способен переписать значение в обход штатного workflow. Поэтому production token должен быть минимально доступен, а опубликованные байты и evidence должны независимо сохраняться в GitHub artifacts/release evidence.

### 5.3. GitHub Environment не имеет подтверждённой защиты

Для `update-staging` и `update-production` сейчас подтверждены `protection_rules=[]`; branch policy не настроена. Следствия:

- нет обязательного ручного approval production deploy;
- нет доказанного ограничения публикации только веткой `main`;
- `secrets: inherit` может передать production secrets изменённому reusable workflow из разрешённой feature-ветки.

До stable нужно включить отдельное обязательное подтверждение production и разрешить production workflow только из защищённой `main`.

### 5.7. Не закрыт жизненный цикл ключа обновлений

Сейчас клиент доверяет одному active Ed25519 public key, а подпись выполняется соответствующим приватным ключом из защищённого локального пути. Само наличие рабочего ключа подтверждено, но для коммерческого релиза этого недостаточно.

До stable необходим отдельный P1-процесс:

- минимум две независимо проверенные зашифрованные резервные копии приватного ключа;
- проверка восстановления ключа без публикации его содержимого;
- назначенный владелец и журнал каждого использования;
- срок действия и плановая ротация ключа;
- заранее встроенный следующий public key до смены signing key;
- подписанная процедура отзыва скомпрометированного ключа;
- аварийный halt-каталог и офлайн-инструкция восстановления доверия;
- доказательство, что старый отозванный ключ больше не может выпустить принимаемый клиентом каталог.

Приватный ключ запрещено сохранять в репозитории, чатах, Actions artifacts и открытых журналах.

### 5.8. Нет измеримой canary-телеметрии

Переход `5% → 25% → 100%` нельзя выполнять только по отсутствию жалоб. До stable необходимо собирать обезличенные события:

- build/channel/catalog sequence;
- download started/verified/failed;
- apply started/completed/failed;
- restart и health confirmation;
- automatic rollback и его причина;
- код ошибки без заказов, адресов, ФИО, паролей, токенов и содержимого БД.

Предлагаемые stop-пороги для каждого этапа canary:

- любое подтверждённое повреждение/исчезновение данных, нарушение company/warehouse scope либо криптографическая ошибка релизного артефакта: немедленный halt, допустимое значение `0`;
- любое отсутствие рабочего rollback после неуспешного apply: немедленный halt, допустимое значение `0`;
- apply + restart + health: не ниже `99%` среди устройств, которые полностью скачали и проверили пакет;
- автоматический rollback из-за дефекта новой версии: не выше `1%`;
- crash rate новой версии не выше baseline более чем на `0,5` процентного пункта;
- наблюдение каждого этапа не меньше 24 часов и не меньше 20 подходящих устройств; если клиентов меньше 20 — все доступные canary-устройства и ручное решение перед расширением.

До появления такой телеметрии и согласованных порогов canary считается `NOT READY`.

## 9. Жёсткие stop-условия

Публикация или расширение canary немедленно останавливается, если:

- любой обязательный тест нестабилен или падает;
- build SHA не совпадает с принятым `main` SHA;
- нет provenance/manifest/hash evidence;
- backup не подтверждён;
- channel/proof/journal не совпадают;
- health не подтверждён после restart;
- изменились или исчезли пользовательские данные;
- появилась повторная команда, дубль или нарушение warehouse/company scope;
- rollback не запускается либо не восстанавливает рабочую версию;
- production workflow может быть запущен без требуемого approval;
- deployed service не соответствует принятому source.

## 10. Что не является релизным блокером

По прямому решению владельца отсутствие Windows Authenticode-подписи не блокирует выпуск. Пользователь Windows может увидеть «Неизвестный издатель»; это принято как известное ограничение.

Это решение не отменяет обязательные SHA-256, подписанный update catalog, payload manifest, installer gate и rollback.

## 11. Требуется ли сейчас действие владельца

Прямо сейчас новые пароли или действия владельца не требуются.

Перед следующим живым шагом понадобятся:

- повторный вход в JustFun, потому что текущая cloud session истекла;
- непосредственное подтверждение перед установкой staging-bootstrap;
- непосредственное подтверждение перед фактическим применением обновления/отката.

До устранения source/build/pipeline блокеров просить владельца вводить пароли или устанавливать сборку рано.

## 12. Критерий окончательного GO

Релиз получает `GO` только одновременно при выполнении всех условий:

- clean `main` и точный финальный SHA;
- зелёные обязательные CI и Windows gate;
- attested installer/payload/manifest;
- свежая проверенная backup;
- живой update, restart, health, rollback и restore;
- сохранность данных до и после каждого перехода;
- полный ТЗ №3 на финальном RC;
- два пользователя, два склада и два устройства;
- production VPS/DB/Telegram/address acceptance;
- проверенный backup/restore/rotation/revocation signing key;
- каждый открытый P0 закрыт доказательством;
- каждый P1 закрыт доказательством либо владелец явно и документированно исключил соответствующую функцию из состава этого релиза;
- защищённый production workflow;
- измеримая обезличенная canary-телеметрия и выполненные stop-пороги;
- точный released-commit и повторно собранные из него installer/payload;
- stable canary `5% → 25% → 100%` без критических ошибок;
- финальный evidence-пакет с вердиктом `GO`; текущий генератор evidence намеренно остаётся в состоянии `NO_GO / NOT_RUN`.

До выполнения этого списка единственный честный статус — **NO-GO**.
