# Актуальный статус релиза JustFun

Дата проверки: 26 августа 2026 года.

## Краткий вердикт

**Статус: NO-GO — публичный релиз пока запускать нельзя.**

Версия 7.8.4 уже собрана как полноценный Windows-кандидат. Установщик прошёл установку, запуск, удаление и сохранение пользовательских данных. Подписанное обновление опубликовано в staging, а установленная 7.8.3 успешно проверила подпись и полностью скачала точный пакет 7.8.4. Причины двух красных проверок исправлены и новый staging sequence 2 подписан, но повторные GitHub runs и публикация через Actions ещё не завершены. Обновление не применялось, откат не доказан, stable-каталог не опубликован, а часть ТЗ №3 не завершена на втором ПК и в финальной установленной 7.8.4.

## Что блокирует релиз

- Постоянный `audit-ledger` синхронизирован коммитом `088a1dcabffb1e76d89b05ff441b59b18348cf27`; локальный `verify-ledger` подтвердил 83 теста и 0 ошибок.
- Source-hygiene и ограничение пути архива исправлены коммитом `c5396fe6703e719350a5043c75e36131a040b0bd`.
- Publication workflow и защита sequence исправлены коммитом `298ea06aa707d4f074557ddb4deeaf869faa6666`.
- Локально пройдены catalog operations `31/31`, Worker `23/23`, YAML `9/9`, release contract `83/83`, source-hygiene и PowerShell syntax.

PR #26 остаётся Draft. До зелёных повторных запусков на точном новом HEAD выпуск запрещён.

### 2. Новый Cloudflare-токен ещё не доказал запись через GitHub Actions

Последний `Publish staging update catalog`, run `32858886678`, запускался до замены секретов и завершился ошибкой отсутствующих environment secrets. После обновления токена workflow ещё не перезапускался.

Подготовлен и проверен подписанный staging sequence `2`, SHA-256 `d9bad4f4fa2cafcdc23759bc3bf012018fbc07a3deb72f7cd31d6f6a3ff21ae5`. Он нужен, чтобы новый run доказал реальную запись KV, сохранение предыдущего sequence `1` и точное публичное совпадение байтов.

### 3. Не завершён живой цикл обновления

Обязательная последовательность:

1. применить подписанное обновление 7.8.3 → 7.8.4;
2. перезапустить программу;
3. подтвердить версию, вход владельца, склад, заказы, остатки, настройки, VPS и журналы;
4. доказать health confirmation;
5. опубликовать подписанный rollback и доказать автоматическое восстановление;
6. только после этого открывать stable-canary.

### 4. Не завершён полный живой повтор ТЗ №3 на финальной 7.8.4

Нужно повторно проверить исправленные дефекты и весь основной бизнес-путь: четыре разных заказа, подбор товаров, маршруты, статусы, водители, отчёты, оплаты, архив, удаление, восстановление, печать/PDF, настройки, все кнопки и журналы.

### 5. Не выполнена обязательная многопользовательская проверка

Нужны второй пользователь и второй ПК/профиль: права доступа, второй склад, одновременные изменения, конфликт версий, offline/reconnect, outbox, изоляция компаний и складов.

### 6. Остались внешние функциональные блокеры

- адресный production-provider и массовая матрица реальных адресов не приняты;
- команда в реальной Telegram-группе, входящие/исходящие события и повторная доставка не проверены;
- полная матрица переходов старых схем БД и восстановление каждой исторической копии не доказаны;
- полный визуальный PASS всех состояний и размеров окон не завершён.

### 7. Stable ещё не существует

Production Worker работает, но stable-каталог сейчас отвечает HTTP 404. Стабильного GitHub Release нет. После полного staging acceptance требуется canary `5% → 25% → 100%`, затем стабильный non-prerelease Release.

## Порядок завершения

1. Получить зелёные повторные GitHub-проверки для уже зафиксированных исправлений на точном HEAD.
2. Повторно запустить staging publication с новым токеном и получить SUCCESS.
3. Сделать резервную копию установленной 7.8.3.
4. Применить 7.8.4 через штатный updater и выполнить полный post-update контроль данных и журналов.
5. Повторить все исправленные живые дефекты и основной бизнес/UI-цикл.
6. Доказать подписанный rollback.
7. Завершить второй ПК/пользователя, свежую миграцию VPS, Telegram-группу и адресный acceptance.
8. Выпустить stable-canary 5%, затем 25%, затем 100% только при отсутствии критических ошибок.
9. Создать стабильный GitHub Release и зафиксировать финальные SHA-256, журналы и откат.

## Отдельное решение владельца

Отсутствие Windows Authenticode-подписи не считается блокером по прямому решению владельца. Возможное предупреждение Windows «Неизвестный издатель» принято как известное ограничение.
