# Актуальный статус релиза JustFun

Дата актуализации: 29 августа 2026 года.

## Краткий вердикт

**Статус: NO-GO — публичный релиз пока запускать нельзя.**

29 августа выполнен пакет исходных исправлений по последним находкам владельца и по усилению многопользовательской сессии. По прямому указанию владельца автоматические и живые проверки не запускаются. Поэтому новые изменения имеют только статус `SOURCE FIXED / NOT RETESTED`; будущая сборка без проверок не может получить статус проверенного коммерческого релиза.

После резервного копирования production D1 применена миграция `010-session-binding.sql`, развёрнуты License Worker version `ee721f07-8de6-4d37-98cd-239ff52ffe5c` и company Telegram broker version `7621fc59-542c-46e7-b595-a5bc539c070c`. Health- и live-проверки после развёртывания не запускались по указанию владельца; native Telegram Workers и REG VPS не обновлялись. Эти операции не меняют общий статус `NO-GO`.

**Живая приёмка владельцем: FAIL.** Переданный как готовый установщик `7.8.4` отклонён уже примерно за первые десять минут неполной пользовательской проверки. Обнаружены критические отказы VPS-синхронизации и завершения самовывоза, отсутствие текстового поиска адресов, невозможность нового сотрудника получить назначенный склад, отсутствующий серверный метод списка приглашений, рассогласование отображаемой версии и несколько непринятых UX-сценариев. Пользователь проверил только часть программы, поэтому полный объём дефектов пока неизвестен.

Последующий запуск исправленной рабочей копии подтвердил важный прогресс: владелец и сотрудник в двух изолированных профилях успешно обменялись изменениями через VPS в обе стороны и сохранили одинаковое состояние после полного перезапуска. После production-обновления License Worker отдельно пройден свежий путь `создание приглашения → принятие → назначенный склад → перезапуск → выход → обычный повторный вход` в третьем изолированном профиле. Это частичный живой PASS многопользовательского режима, но не основание для релиза: два физических ПК, конфликты, offline/reconnect, изменение прав активной сессии и изоляция компаний/складов ещё не приняты.

Отдельно закрыт production-дефект Telegram-авторизации сотрудника с русскоязычной ролью. Вместо рискованного обновления broker contract `1 → 4` развёрнут минимальный совместимый hotfix `1.0.3`: preview, canary и полный rollout прошли, после чего живой `employee.live2` больше не получил `AUTH_SERVICE_INVALID`. Ответ `TELEGRAM_NOT_CONFIGURED` подтверждает, что запрос теперь проходит авторизацию и доходит до фактического состояния компании. Реальная настройка Telegram этой тестовой компании, группа, сообщения и кнопки ещё не приняты, поэтому общий статус остаётся `NO-GO`.

Название каталога `READY-RELEASE` и прежняя передача этого Setup как готового релиза признаны ошибочными. Артефакт является только не прошедшей живую приёмку тестовой сборкой. Автоматические, CI, installer и source-проверки не заменяют полный пользовательский сценарий установленной программы и не дают оснований для статуса `GO`.

Подписанный staging sequence 2 опубликован корректно, но применять его к рабочей 7.8.3 запрещено: живая проверка обнаружила, что установленная 7.8.3 всегда выбирает встроенный канал `stable`, а прежний payload 7.8.4 после перезапуска также теряет принятый `staging`. Это могло завершить проверку обновления откатом либо ошибкой состояния. Дефект исправлен коммитом `609b99dfe77186ddbe07b95903bd2263718cec60`: канал теперь восстанавливается только из проверенного подписанного proof и при потере/подмене proof работает fail-closed. Локальные updater-регрессии прошли; PR-гейты `32983630712` и `32983630661` завершены успешно. PR Windows-run собрал временный merge SHA `9dc93854...`, поэтому не используется как релизный артефакт. Отдельный полный workflow_dispatch `32984663174` запущен на точном SHA `609b99d...`; новый staging sequence 3 ожидает его результат. Обновление и откат не применялись; stable не опубликован.

## Что блокирует релиз

### 1. Не завершён живой цикл обновления

Обязательная последовательность:

1. завершить Windows gate коммита `609b99d`, собрать и опубликовать новый payload 7.8.4 как immutable staging sequence 3;
2. установить проверенный staging-bootstrap 7.8.3, отличающийся от исходного переходника только `default_channel: stable → staging`;
3. применить подписанное обновление 7.8.3 → 7.8.4;
4. перезапустить программу;
5. подтвердить версию, вход владельца, склад, заказы, остатки, настройки, VPS и журналы;
6. доказать health confirmation;
7. опубликовать подписанный rollback и доказать автоматическое восстановление;
8. только после этого открывать stable-canary.

### 2. Не завершён полный живой повтор ТЗ №3 на финальной 7.8.4

Нужно повторно проверить исправленные дефекты и весь основной бизнес-путь: четыре разных заказа, подбор товаров, маршруты, статусы, водители, отчёты, оплаты, архив, удаление, восстановление, печать/PDF, настройки, все кнопки и журналы.

### 3. Не выполнена обязательная многопользовательская проверка

Базовый обмен между владельцем и сотрудником в двух изолированных профилях одного ПК, серверное подтверждение, нулевой outbox и повторное чтение после перезапуска пройдены. Свежий цикл приглашения, автоматическое восстановление сессии и обычный повторный вход также пройдены в третьем профиле. Ещё нужны второй физический ПК, второй склад, изменение прав активной сессии, одновременные изменения, конфликт версий, offline/reconnect, изоляция компаний и складов.

### 4. Остались внешние функциональные блокеры

- production License Worker обновлён до `auth_contract: 5`, а путь создания/принятия приглашения прошёл. Живые сценарии отзыва, истечения, повторного использования и конкурентного принятия ещё не выполнены;
- адресный production-provider и массовая матрица реальных адресов не приняты;
- команда в реальной Telegram-группе, входящие/исходящие события и повторная доставка не проверены;
- полная матрица переходов старых схем БД и восстановление каждой исторической копии не доказаны;
- полный визуальный PASS всех состояний и размеров окон не завершён.

### 5. Stable ещё не существует

Production Worker работает, но stable-каталог сейчас отвечает HTTP 404. Стабильного GitHub Release нет. После полного staging acceptance требуется canary `5% → 25% → 100%`, затем стабильный non-prerelease Release.

## Порядок завершения

1. Сделать резервную копию установленной 7.8.3.
2. Применить 7.8.4 через штатный updater и выполнить полный post-update контроль данных и журналов.
3. Повторить все исправленные живые дефекты и основной бизнес/UI-цикл.
4. Доказать подписанный rollback.
5. Завершить второй ПК/пользователя, свежую миграцию VPS, Telegram-группу и адресный acceptance.
6. Выпустить stable-canary 5%, затем 25%, затем 100% только при отсутствии критических ошибок.
7. Создать стабильный GitHub Release и зафиксировать финальные SHA-256, журналы и откат.

## Отдельное решение владельца

Отсутствие Windows Authenticode-подписи не считается блокером по прямому решению владельца. Возможное предупреждение Windows «Неизвестный издатель» принято как известное ограничение.
