# Многопользовательская архитектура данных и автоматические миграции

## 1. Назначение

Документ определяет обязательную архитектуру JustFun для коммерческой эксплуатации тысячами компаний. Он распространяется на PostgreSQL VPS, локальные данные Windows-клиента, Telegram/Cloudflare D1, серверные API и механизм обновления программы.

Обязательная автономная матрица для каждой поддерживаемой старой схемы, аварийных остановок, повторов и реального восстановления определена в [`UNATTENDED-E2E-AND-DATABASE-MIGRATION-SPEC.md`](UNATTENDED-E2E-AND-DATABASE-MIGRATION-SPEC.md).

Цель: новая версия приложения должна безопасно работать с данными предыдущих поддерживаемых версий, автоматически выполнять только заранее подготовленные миграции, не смешивать компании и не привязывать старые тестовые записи к новому клиенту.

«Автоматически подстраивать базу» означает детерминированно применять подписанные и протестированные миграции по номеру версии. Запрещено динамически менять таблицы на основании случайного содержимого клиентских данных.

## 2. Подтверждённая исходная реализация

В исходном коде уже присутствуют отдельные необходимые элементы:

- PostgreSQL `schema_migrations`;
- ключи `workspace_id/company_id + warehouse_id + environment`;
- `business_records_v3`, события, команды и идемпотентный `command_id`;
- PostgreSQL RLS и принудительный tenant scope;
- optimistic entity versions;
- Telegram D1 migrations `0001`–`0003`;
- Telegram scope по `installation_id`, `company_id`, `environment`, `warehouse_id`;
- запрет автоматической привязки части legacy Telegram-состояния к другой компании или складу.

Это является хорошей основой, но не доказывает готовность к тысячам компаний. Не подтверждены production-миграции старых баз, смешанные версии клиентов, автоматический rollback, карантин legacy-данных, массовое обновление Telegram-инсталляций и шардирование.

## 3. Обязательная модель идентичности

Каждая запись и команда должны иметь полный неизменяемый scope:

| Поле | Назначение |
|---|---|
| `tenant_id` / `company_id` | юридически и логически отдельная компания |
| `warehouse_id` | склад внутри компании |
| `environment` | `live`, `demo`; QA должен находиться в отдельном deployment/database namespace |
| `installation_id` | конкретная серверная/Telegram-инсталляция |
| `device_id` | конкретный Windows-клиент |
| `actor_user_id` | пользователь, выполнивший действие |
| `entity_id` | стабильный идентификатор сущности |
| `command_id` | стабильный идентификатор повторяемой команды |
| `schema_version` | версия физической схемы хранения |
| `data_contract_version` | версия структуры payload |
| `api_contract_version` | версия протокола клиент–сервер |

Запись без подтверждённого `company_id`, `warehouse_id` или environment не может автоматически попасть в рабочую область. Она переводится в legacy quarantine.

## 4. Физическое и логическое разделение

### 4.1. PostgreSQL VPS

Один PostgreSQL-кластер может обслуживать несколько компаний только при выполнении всех условий:

1. tenant scope входит во все первичные/уникальные ключи и индексы;
2. RLS включён и `FORCE ROW LEVEL SECURITY` применяется ко всем бизнес-таблицам;
3. scope устанавливается внутри транзакции после серверной проверки лицензии и разрешений;
4. фоновые задания также получают явный tenant scope;
5. SQL без tenant predicate запрещается автоматическими тестами;
6. резервное копирование позволяет восстановить отдельного tenant либо безопасно восстановить кластер целиком;
7. аудит содержит tenant, warehouse, actor, device, command и correlation id.

При росте нагрузки компании распределяются по shard/database group. Маршрутизация выполняется control plane по `tenant_id`, а не клиентом. Крупной компании может быть выделен отдельный кластер без изменения клиентского API.

### 4.2. Telegram/Cloudflare

У каждой компании собственны:

- один или несколько Telegram-ботов;
- токены ботов и ключи подключения;
- company installation profile;
- складские chat bindings;
- водительские bindings;
- webhook secret и client API key;
- политика ротации и отзыва.

Допускаются три режима:

1. `managed-shared` — общий Worker/control plane, но строгий логический tenant scope;
2. `managed-dedicated` — отдельный Worker/D1/Secrets namespace компании;
3. `self-managed` — инфраструктура клиента, подключённая через проверенный connector profile.

Режим является свойством `connection_profile`, а не условием бизнес-логики. Смена режима не должна менять `company_id`, `warehouse_id`, маршруты и историю статусов.

D1 не предоставляет PostgreSQL RLS, поэтому tenant isolation обязан проверяться в каждом Worker handler и во всех составных ключах/индексах. Запрос по одному `warehouse_id` без `installation_id/company_id` запрещён.

### 4.3. Тестовые базы

Текущие тестовые VPS и Telegram-базы нельзя считать чистыми.

- QA использует отдельный deployment или отдельный database namespace.
- Названия тестовых компаний не заменяют техническую изоляцию.
- LIVE-клиент не должен получать QA credentials/endpoints.
- DEMO внутри компании изолируется environment, но нагрузочные и миграционные тесты не запускаются в production database.
- Перед каждым циклом сохраняется inventory старых tenant/scope/schema versions.
- Старые тестовые данные не удаляются автоматически: сначала backup, отчёт, quarantine, затем отдельное подтверждённое удаление.

## 5. Реестр миграций

Для каждой физической базы требуется таблица/реестр:

| Поле | Требование |
|---|---|
| `migration_id` | монотонный уникальный номер |
| `name` | стабильное имя |
| `checksum_sha256` | контроль неизменности миграции |
| `component` | VPS, broker, Telegram Worker, local client |
| `from_version` / `to_version` | допустимый переход |
| `phase` | expand, backfill, verify, contract |
| `status` | pending, running, applied, failed, rolled_back |
| `started_at` / `finished_at` | аудит времени |
| `application_version` | версия deployer |
| `backup_id` | копия перед опасной фазой |
| `error_code` | безопасная причина без секретов |

Изменение уже применённого файла миграции запрещено. Исправление создаётся новой миграцией.

## 6. Алгоритм безопасного автоматического обновления

### Фаза 0 — preflight

1. Проверить backup и свободное место.
2. Прочитать текущую schema/data/API version.
3. Сверить checksum всех применённых миграций.
4. Проверить минимальную и максимальную поддерживаемую версию клиента.
5. Запустить tenant inventory и поиск orphan/legacy rows.
6. При неизвестной схеме остановиться без изменения данных.

### Фаза 1 — expand

- добавлять новые nullable columns/tables/indexes;
- не удалять старые поля;
- не переименовывать поле одним шагом;
- сервер временно читает старый и новый форматы;
- новые записи могут dual-write в оба формата только при проверенной идемпотентности.

### Фаза 2 — backfill

- обрабатывать данные малыми idempotent batches;
- хранить cursor/checkpoint;
- ограничивать нагрузку;
- валидировать tenant scope каждой строки;
- повторять после сбоя без дублей;
- неоднозначные legacy rows отправлять в quarantine.

### Фаза 3 — verify

- сравнить counts, digests и обязательные поля;
- проверить foreign keys, уникальность и RLS;
- выполнить cross-tenant negative tests;
- проверить чтение клиентами поддерживаемых версий;
- заблокировать contract phase при любом расхождении.

### Фаза 4 — contract

Удаление старых columns/tables и прекращение старого API допускаются только после подтверждения, что поддерживаемые клиенты обновлены и rollback window завершён. Contract-миграция выпускается отдельно от expand.

## 7. Совместимость версий

Сервер публикует capability document:

```text
api_contract_current
api_contract_min_supported
schema_version
data_contract_versions_supported
required_client_version
migration_state
maintenance_mode
```

Правила:

- новый сервер сначала совместим минимум с текущей и предыдущей поддерживаемой версией клиента;
- новый клиент проверяет capability до отправки команд;
- несовместимый клиент получает понятный `CLIENT_UPGRADE_REQUIRED`, а не повреждает данные;
- migration-in-progress разрешает только явно безопасные операции;
- критические операции fail-closed;
- локальная outbox хранит исходную contract version и преобразуется детерминированным adapter.

## 8. Конфликты и старые данные

### 8.1. Legacy quarantine

Неоднозначная запись получает:

- исходную таблицу и primary key;
- безопасный payload snapshot/digest;
- предполагаемые scopes и причину неоднозначности;
- migration id;
- статус `unresolved | assigned | rejected | archived`.

Запрещено автоматически назначать старую запись первой найденной компании, складу или Telegram-инсталляции.

### 8.2. Optimistic conflicts

При несовпадении `base_version` сервер возвращает текущую версию и код конфликта. Клиент не повторяет команду с новым base version автоматически, если это меняет бизнес-смысл. Разрешены только:

- безопасный field-level merge по утверждённым правилам;
- повтор чтения и явное подтверждение пользователя;
- автоматический retry неизменившейся идемпотентной команды.

### 8.3. Идемпотентность

Повтор одного `command_id` внутри одного tenant/warehouse/environment обязан вернуть прежний результат. Тот же `command_id` в другом scope не считается той же операцией и не должен раскрывать чужой результат.

## 9. Provisioning новой компании

Создание компании должно быть одной управляемой операцией:

1. создать tenant identity;
2. назначить database shard;
3. создать owner и первый warehouse;
4. выпустить scoped credentials;
5. создать пустое подтверждённое server state;
6. при необходимости создать Telegram connection profile;
7. выполнить health и tenant-isolation smoke;
8. только после этого разрешить рабочие операции.

Сбой provisioning откатывает незавершённые ресурсы или оставляет resumable operation. Полусозданная компания не должна быть видна другим tenant и не должна использовать global fallback credentials.

## 10. Масштабирование до тысяч компаний

Обязательные механизмы:

- connection pooling с лимитами на процесс и tenant;
- per-tenant rate limits и quotas;
- очереди для migrations, Telegram delivery и outbox;
- shard routing и перенос tenant между shard с двойной проверкой digest;
- partitioning/archive для событий и аудита;
- canary rollout по группе tenant;
- pause/rollback отдельной миграции без остановки всех компаний;
- метрики ошибок, latency, queue age, conflict rate и migration progress;
- отсутствие tenant IDs высокой кардинальности в неограниченных metric labels;
- аварийный read-only mode вместо повреждающей записи.

## 11. Обязательная приёмочная матрица

Проверить минимум:

1. чистая новая база;
2. текущая тестовая база с существующими данными;
3. база предыдущей поддерживаемой версии;
4. база с незавершённой миграцией;
5. повтор той же миграции;
6. rollback после expand и после частичного backfill;
7. старый клиент + новый сервер;
8. новый клиент + старый сервер;
9. два клиента разных поддерживаемых версий;
10. одинаковые warehouse IDs в двух компаниях;
11. попытка чтения и записи чужого tenant;
12. одинаковый command id в разных scopes;
13. Telegram-боты двух компаний в одной общей инфраструктуре;
14. замена Telegram connection profile без потери bindings;
15. отключение одного tenant без влияния на остальные;
16. нагрузочный прогон множества компаний и параллельная миграция canary-группы.

## 12. Release gate

Релиз запрещён, если:

- schema version неизвестна или checksum миграции изменён;
- старые записи автоматически прикрепляются к новой компании;
- запрос работает без полного tenant scope;
- миграция не идемпотентна;
- нет backup/verify/rollback;
- новый сервер сразу ломает предыдущий поддерживаемый клиент;
- Telegram credentials или bindings могут пересечь компании;
- тестовая база используется как production namespace;
- live-проверка смешанных версий и cross-tenant isolation не завершена.
