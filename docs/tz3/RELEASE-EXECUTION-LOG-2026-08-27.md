## 2. Исправления текущего этапа

### 2.1. Local-first и многоскладская синхронизация

Исправлены три гонки, способные повредить или потерять локальное состояние:

1. Фоновая отправка теперь захватывает компанию, склад, среду, scope и epoch до асинхронного ожидания. После смены контекста устаревшая операция прекращается до записи в outbox и до изменения состояния нового склада.
2. Для одного логического scope используется один экземпляр outbox. Drain сериализуется по логическому scope, поэтому переход `A → B → A` не создаёт две параллельные записи одного документа очереди.
3. Критическая операция блокирует смену склада, рабочей/учебной среды, logout, штатный reload и `beforeunload` до подтверждения VPS либо полного дискового отката. Результат `whenPersisted()` проверяется и после мутации, и после отката.

При неподтверждённом дисковом откате устанавливается постоянная блокировка смены контекста: программа не продолжает работу так, будто откат состоялся.

### 2.3. Защита публикации обновлений

Публикация release-каталога теперь требует точные `build-identity.json` и `BUILD-MANIFEST.json`, связывает commit, build ID, release contract и payload, запрещает грязный source и не принимает артефакт из pull request. Stable разрешён только для статуса `released`; staging — для `candidate` либо `released`. Исторические halt/rollback проверяются отдельно от текущей сборки.

### 2.4. Неопределённый результат записи на VPS

После отправки команды транспортная ошибка, потерянный ответ или повреждённый ACK больше не считаются окончательным отказом. Ordinary outbox, журнал склада и critical `pending_server` сохраняются, а клиент повторяет исходный `command_id`. Откат и очистка журнала разрешены только для подтверждённого non-retryable отказа. Runtime-тесты подтвердили сценарии post-commit lost/malformed ACK для обычной операции, критической операции и записи склада.

Перенос локальной компании теперь проверяет владельца, `allWarehouses=true` и глобальные разрешения до первой записи в серверный реестр. Admin и ограниченный owner отклоняются до записи; полный owner допускается.

### 2.5. Сборщик Windows

Публикация неполного либо повреждённого EXE блокируется до появления обязательных PE, runtime и crash-recovery evidence. Для полного payload `411 227 803` байта упаковка переведена с неприемлемо медленного `/SOLID lzma` на проверенный `zlib`: engine собран за `12:51`, Premium wrapper за `9:29`. Точный benchmark прошёл PE `5/5`, crash/recovery `4/4`; engine и Premium fail-closed probes завершились ожидаемым кодом `10` без начала распаковки.
