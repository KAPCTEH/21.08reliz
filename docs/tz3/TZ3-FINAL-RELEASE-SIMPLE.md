# ТЗ №3: окончательный релиз JustFun простыми словами

## Статус документа

Это полный проект требований для согласования с владельцем. Документ описывает, **какой программа должна стать к окончательному коммерческому релизу** и как её безопасно передать клиентам.

Перечисленные функции нельзя считать готовыми только потому, что они записаны в этом ТЗ. Готовность подтверждается исходным кодом, автоматическими проверками, установленной программой, живыми сценариями, журналами и итоговым релизным отчётом.

## 1. Какой должна стать программа

JustFun должна быть одной полноценной Windows-программой для работы с заказами, складами, товарами, водителями, маршрутами, статусами, отчётами и Telegram.

Программа должна подходить:

- небольшой компании с одним компьютером и без собственного сервера;
- компании с несколькими компьютерами и сотрудниками;
- компании с несколькими складами;
- компании со своим VPS;
- большому числу независимых компаний, которые не видят данные друг друга;
- компаниям со своими Telegram-ботами и настройками подключений.

Главный принцип: обычная работа не должна полностью останавливаться только из-за отсутствия VPS, Telegram или временного отключения интернета.

## 2. Что получает клиент

Клиент получает:

1. один установщик Windows;
2. понятную установку без ручного копирования файлов;
3. активацию лицензии и вход в свою компанию;
4. выбор способа хранения данных;
5. полноценную рабочую программу;
6. автоматические обновления без постоянной переустановки;
7. резервное копирование и восстановление;
8. понятную диагностику при проблемах;
9. инструкцию для обычного пользователя;
10. стабильный канал получения исправлений.

Сертификат издателя Windows не является обязательным условием релиза по решению владельца. Поэтому Windows может показывать предупреждение «Неизвестный издатель». Это не должно мешать самой установке и работе программы.

## 3. Путь клиента от покупки до начала работы

### 3.1. Получение программы

Клиент получает официальную ссылку на стабильный установщик. Рядом должны быть указаны:

- название и версия программы;
- дата выпуска;
- краткий список изменений;
- системные требования;
- контрольная сумма файла;
- простая инструкция по установке;
- способ обращения в поддержку.

Временный файл из GitHub Actions не должен быть единственным способом получения программы: такие файлы имеют срок хранения и неудобны обычному клиенту.

### 3.2. Установка

Установщик должен:

- проверить совместимую версию Windows;
- показать понятные шаги;
- установить программу и ярлыки;
- не удалять пользовательские данные при обычном обновлении;
- уметь исправить повреждённую установку;
- корректно удалить программу;
- отдельно спросить, нужно ли удалять рабочие данные при полном удалении;
- сохранить журнал установки без паролей и токенов;
- при ошибке вернуть систему в рабочее состояние.

### 3.3. Первый запуск

При первом запуске клиент должен увидеть последовательный мастер:

1. активация лицензии или вход в существующую компанию;
2. создание владельца либо вход приглашённого сотрудника;
3. создание или выбор компании;
4. создание первого склада;
5. выбор способа хранения данных;
6. необязательное подключение VPS;
7. необязательное подключение Telegram;
8. краткая проверка готовности;
9. открытие главного рабочего экрана.

VPS и Telegram не должны быть обязательными для первого знакомства и локальной работы.

## 4. Два способа хранения данных

Пользователь выбирает один из двух понятных режимов.

### 4.1. Режим «На этом компьютере»

Все рабочие данные хранятся на текущем компьютере.

В этом режиме пользователь может:

- создавать и изменять обычные заказы;
- вести товары и локальные остатки;
- создавать водителей;
- готовить маршруты;
- менять обычные настройки;
- формировать доступные локальные отчёты;
- создавать резервные копии;
- закрывать программу и продолжать работу после повторного запуска.

Ограничения должны быть показаны заранее:

- нет одновременной общей работы нескольких компьютеров;
- нет централизованного серверного восстановления;
- серверные права и критические общие операции недоступны;
- часть внешних функций может требовать интернет или поддерживаемый сервер.

Локальный режим не является временной демонстрацией. Он должен быть полноценным вариантом использования для одного автономного рабочего места.

### 4.2. Режим «Сервер и несколько компьютеров»

На каждом компьютере остаётся локальная рабочая копия, а подтверждённые общие данные синхронизируются с сервером.

Этот режим даёт:

- совместную работу нескольких пользователей и компьютеров;
- единые склады, заказы, маршруты и статусы;
- централизованные роли и права;
- серверные резервные копии;
- подключение интеграций;
- общую историю изменений;
- восстановление работы после временного обрыва связи.

Пользователь всегда должен видеть состояние записи:

- `Сохранено на компьютере`;
- `Ожидает синхронизации`;
- `Синхронизировано`;
- `Требуется решить конфликт`;
- `Сервер недоступен`;
- `Ошибка отправки`.

Надпись `Сохранено` без объяснения, где находятся данные, запрещена.

## 5. Как устроить оба режима правильно

Не нужно разрабатывать две разные программы. Локальная база должна использоваться всегда.

- В локальном режиме она является главным хранилищем.
- В серверном режиме она хранит рабочую копию и очередь изменений, а сервер подтверждает общее состояние.

Так программа продолжает обычную работу при временном отсутствии сети. После восстановления связи она отправляет накопленные изменения без создания дублей.

Критические операции нельзя подтверждать только локально. К ним относятся права доступа, окончательное списание общего остатка, удаление склада и другие действия, которые могут повредить совместную работу. Программа должна честно объяснить, почему для конкретной операции нужен сервер.

## 6. Переход с локального хранения на VPS

Клиент может сначала выбрать локальную работу, а позднее подключить сервер. Переустанавливать программу и повторно вводить все данные не требуется.

В настройках должна быть кнопка `Подключить сервер и перенести данные`.

### 6.1. До переноса

Программа автоматически:

- проверяет локальную базу;
- создаёт резервную копию;
- считает заказы, товары, водителей, маршруты, склады и другие записи;
- проверяет связи между ними;
- проверяет сервер и совместимость его версии;
- определяет, пустая ли серверная компания;
- показывает пользователю, что будет перенесено.

### 6.2. Если сервер пуст

Программа создаёт защищённое пространство компании и переносит данные небольшими повторяемыми пакетами. Если интернет пропал, перенос продолжается с последнего подтверждённого места, а не начинается заново.

### 6.3. Если на сервере уже есть данные

Программа не имеет права молча заменить одну базу другой. Она предлагает:

1. перенести локальные данные в новый склад или отдельное рабочее пространство;
2. выполнить управляемое объединение и показать спорные записи;
3. отменить перенос.

Остатки, оплаты, права, удаление и завершённые рейсы не объединяются случайным автоматическим выбором.

### 6.4. После загрузки

Программа повторно читает данные с сервера и сравнивает:

- количество записей;
- уникальные номера записей;
- связи заказов, маршрутов, водителей и товаров;
- остатки и движения;
- статусы и удаления;
- контрольные суммы данных;
- число конфликтов и отклонённых операций.

Только после полного совпадения программа переключается в серверный режим. Исходная локальная копия сохраняется для возможного возврата. Пользователь получает итоговый отчёт о переносе.

При любой ошибке программа остаётся в исходном локальном режиме и не теряет данные.

## 7. Какие серверы поддерживать

Для первого коммерческого релиза рекомендуется поддержать:

1. локальное хранение;
2. официальный сервер JustFun;
3. VPS клиента, на котором установлена проверенная серверная часть JustFun.

Нельзя обещать подключение к любой произвольной базе, CRM или облаку. Для каждой другой системы нужен отдельный проверенный адаптер. Такие адаптеры можно добавлять после основного релиза без переделки всей программы.

## 8. Компании, склады, пользователи и права

Каждая компания должна иметь собственную защищённую область данных.

Обязательно:

- одна компания не видит другую;
- новый склад не получает товары, заказы, водителей и настройки старого склада без явного переноса;
- DEMO и реальные данные разделены;
- пользователь видит только разрешённые компании и склады;
- владелец создаёт сотрудников и назначает доступные роли;
- отключённый сотрудник теряет доступ;
- смена роли начинает действовать на других компьютерах;
- важные изменения прав записываются в историю;
- секреты Telegram и VPS не показываются обычным сотрудникам;
- удаление компании, склада или пользователя требует отдельного подтверждения и безопасной проверки зависимостей.

Для каждой записи должны сохраняться компания, склад, среда, автор, устройство и время изменения. Это нужно для защиты от смешивания данных и для расследования ошибок.

## 9. Старые базы и обновление структуры данных

Новая версия программы должна уметь безопасно читать данные поддерживаемых старых версий.

При обновлении программа и сервер:

1. определяют текущую версию базы;
2. создают резервную копию перед опасными изменениями;
3. последовательно применяют заранее подготовленные изменения;
4. проверяют результат;
5. не выполняют одно и то же изменение повторно;
6. останавливаются при неизвестной или повреждённой структуре;
7. помещают непонятные старые записи в отдельный карантин;
8. не приписывают старые данные случайной компании;
9. сохраняют отчёт без паролей и токенов;
10. поддерживают откат либо безопасное продолжение после сбоя.

Старая и новая версия клиента могут ограниченно работать одновременно только в заранее проверенном диапазоне совместимости. Несовместимая версия должна быть остановлена с понятным предложением обновиться.

## 10. Заказы

Заказ должен проходить полный жизненный цикл:

- создание;
- редактирование;
- поиск и фильтрация;
- добавление адреса и контактов;
- добавление товаров или услуг;
- назначение склада;
- включение в маршрут;
- изменение статусов;
- оплата и связанные отметки;
- отмена;
- удаление по правилам;
- отображение в отчётах и истории.

Программа не должна создавать дубль при двойном нажатии, повторной отправке или восстановлении интернета. Удалённый заказ не должен возвращаться после синхронизации другого компьютера.

Перед релизом необходимо создать минимум четыре разных тестовых заказа и провести их разными допустимыми путями до завершения, отмены и удаления.

## 11. Умный поиск адресов

Адрес можно вводить полностью, частично, с сокращениями и обычными опечатками.

Поиск должен понимать:

- города, посёлки, деревни и сёла;
- СНТ, ДНТ, массивы и другие территории;
- улицы, проспекты, шоссе, переулки;
- дома, корпуса, строения и участки;
- длинные и сокращённые формы адреса;
- неполный порядок частей адреса.

В первую очередь живыми тестами проверяются Санкт-Петербург, Ленинградская, Новгородская и Псковская области, Карелия, Москва и Московская область.

Программа показывает до трёх наиболее подходящих вариантов, предупреждает о сомнительном результате и позволяет исправить адрес вручную. Выбранный адрес сохраняет нормальную подпись, координаты и идентификатор поставщика, если он доступен.

Обязательное сравнение с Яндекс Картами не проводится. Качество подтверждается собственным эталонным набором адресов, ошибочных запросов и реальными живыми сценариями.

Если поставщик адресов недоступен, программа не должна терять заполненный заказ. Пользователь получает понятное сообщение и возможность ручного ввода или повторного поиска.

## 12. Товары, остатки и склад

Программа должна поддерживать:

- создание и изменение товаров;
- приход, расход, резерв и возврат;
- привязку движений к складу и заказу;
- защиту от отрицательного или ошибочного остатка по утверждённым правилам;
- историю движения;
- фильтры, поиск и отчёты;
- безопасное удаление или архивирование;
- независимые остатки разных складов;
- защиту от одновременного списания на двух компьютерах.

Критическое окончательное списание общего остатка подтверждается сервером. Локально можно подготовить операцию, но нельзя показывать её как общую завершённую без подтверждения.

## 13. Водители, маршруты и рейсы

Программа должна:

- создавать и редактировать водителей;
- назначать доступного водителя;
- добавлять в маршрут несколько заказов;
- показывать точки на карте;
- предлагать порядок точек, когда доступен маршрутный сервис;
- позволять человеку вручную изменить порядок;
- считать доступные расстояния и время;
- сохранять черновик при недоступности внешнего сервиса;
- проводить рейс через разрешённые статусы;
- фиксировать выдачу, старт, доставку, возврат, закрытие и отмену;
- не позволять одному критическому действию выполниться дважды;
- возвращать резервы и статусы по утверждённым правилам отмены;
- отражать результат в складе и отчётах.

Каждый переход статуса проверяется отдельно. Нельзя закрыть рейс, если обязательные условия не выполнены. Ошибка должна объяснять, что именно требуется исправить.

## 14. Отчётность

Отчёты должны строиться только по данным разрешённой компании, склада и периода.

Проверяются:

- заказы и их статусы;
- доставки и возвраты;
- товары и движения;
- остатки;
- водители и рейсы;
- оплаты, расходы и другие уже предусмотренные показатели;
- фильтры;
- печать;
- экспорт в доступные форматы.

Итог на экране, в печати и в экспортированном файле должен совпадать. Пустой новый склад не должен видеть показатели старого склада.

## 15. Telegram

Новая архитектура общего официального бота, центрального Gateway и `local_mailbox` отменена владельцем. В релизном объёме остаётся существующая Telegram-интеграция без изменения её архитектуры.

Текущий мастер программы использует собственного Telegram-бота компании и отдельную инфраструктуру Cloudflare клиента. В живой приёмке необходимо пройти именно существующий интерфейс и проверить его фактическое поведение. Наличие исходного кода не является доказательством, что подключение уже работает в production.

Telegram-настройки и группы одной компании или склада не должны использоваться другой компанией или складом. Ошибка Telegram не должна изменять основную бизнес-архитектуру программы.

Необходимо проверить:

- подключение;
- подтверждение полномочий;
- привязку группы к конкретному складу;
- отправку маршрута;
- действия водителя;
- получение статусов;
- повторную доставку без дублей;
- временную недоступность Telegram;
- временную недоступность VPS;
- переподключение;
- смену токена;
- полное отключение и удаление привязки;
- отсутствие сообщений в чужой компании или на чужом складе.
- автоматическое определение удаления бота из группы;
- существующий мастер BotFather/Cloudflare без добавления нового общего бота;
- одинаковое фактическое поведение до и после подключения VPS, если иное не предусмотрено текущей реализацией.

Ошибка Telegram не должна блокировать обычное создание заказа. Неотправленные уведомления должны иметь отдельный понятный статус.

## 16. Резервные копии и восстановление

Клиент должен иметь возможность:

- создать локальную резервную копию;
- увидеть дату и результат последней копии;
- сохранить копию в выбранное место;
- восстановить данные через безопасный мастер;
- предварительно увидеть компанию, склад, версию и содержимое копии;
- отказаться от восстановления;
- получить отчёт о результате.

Сервер также должен иметь регулярные резервные копии. Наличие файла копии недостаточно: восстановление необходимо периодически проверять в изолированной среде.

Восстановление не должно тихо смешивать компании, LIVE и DEMO или старую и новую структуру данных.

## 17. Автоматические обновления

Программа должна обновляться без ручного удаления и повторной установки.

Обновление проходит так:

1. программа получает информацию о новой версии;
2. проверяет, подходит ли версия текущему клиенту и серверу;
3. скачивает файл только с разрешённого адреса;
4. проверяет размер, контрольную сумму и криптографическую подпись;
5. создаёт точку восстановления;
6. закрывает программу и устанавливает обновление;
7. обновляет локальную базу безопасными шагами;
8. запускает новую версию и выполняет самопроверку;
9. при неудаче возвращает предыдущую рабочую версию;
10. сохраняет пользовательские данные и настройки.

Криптографическая подпись автоматического обновления обязательна. Это отдельная защита и она не заменяется необязательным сертификатом издателя Windows.

Обновления выпускаются по каналам:

- внутренний тест;
- тестовая компания;
- ограниченный пилот;
- стабильный канал для всех клиентов.

Распространение можно немедленно остановить при обнаружении проблемы.

## 18. Интерфейс и единый стиль

Вся программа должна выглядеть как единый продукт.

Проверяются:

- одно название и логотип на всех экранах;
- единые цвета, шрифты, кнопки, поля, таблицы и уведомления;
- одинаковое поведение `Сохранить`, `Отмена`, `Закрыть`, `Удалить`;
- размеры окон и диалогов;
- прокрутка длинных страниц и таблиц;
- открытие и закрытие окон;
- отсутствие обрезанного текста;
- масштаб Windows;
- маленький и большой экран;
- состояния загрузки, пустого списка и ошибки;
- понятные подтверждения опасных действий;
- работа клавиатуры, мыши и фокуса;
- читаемость текста и контраст;
- отсутствие мёртвых кнопок и невидимых действий.

Каждая кнопка должна давать видимый результат либо ясное объяснение, почему действие сейчас недоступно.

## 19. Безопасность и конфиденциальность

Обязательно:

- соединение с сервером только по защищённому каналу;
- проверка подлинности сервера;
- хранение паролей и токенов средствами защищённого хранилища Windows;
- запрет записи секретов в обычные журналы;
- раздельные секреты компаний и Telegram-подключений;
- проверка прав на сервере, а не только скрытие кнопок;
- защита серверной базы от чтения чужой компании;
- журнал важных действий;
- ограничение частых попыток входа;
- безопасная смена и отзыв ключей;
- проверка установщика и обновлений по контрольным суммам;
- обезличенный диагностический отчёт.

Программа не должна самостоятельно удалять защищённую сессию только из-за временной ошибки Windows. Она должна сохранить данные и предложить безопасный повторный вход.

## 20. Проверка программы перед выпуском

Проверка выполняется на реальной установленной сборке, а не только в исходном коде.

### 20.1. Сначала фиксируется исходная точка

- версия и Git-коммит;
- хеш установщика и программы;
- компания, склад, роль и устройство;
- состояние локальной базы;
- состояние VPS, Telegram и обновлений;
- начало журналов;
- список заранее известных проблем.

### 20.2. Полный обход без изменения данных

Сначала открываются все страницы, вкладки, меню, окна, фильтры и кнопки. Фиксируются внешний вид, доступность, ожидаемое действие и найденные отклонения.

### 20.3. Полный локальный цикл

Без VPS и Telegram создаются товары, водители, четыре заказа, маршруты, статусы и отчёты. Затем программа закрывается и запускается снова. Все допустимые локальные данные должны сохраниться.

### 20.4. Подключение и перенос на VPS

Создаётся backup, выполняется перенос, сравниваются все записи, проверяются повтор и откат. После этого повторяется бизнес-цикл с работающим сервером.

### 20.5. Telegram

Подключаются бот и складская группа, отправляются маршруты, принимаются статусы, проверяются обрывы связи и повторная доставка.

### 20.6. Изоляция

Создаётся новый склад, новый пользователь и отдельная тестовая компания. Они не должны получить чужие данные, права или Telegram-настройки.

### 20.7. Второй компьютер

На втором ПК проверяются вход, синхронизация, одновременные изменения, конфликты, удаления, роли, offline и reconnect.

### 20.8. Установка, обновление и восстановление

Проверяются:

- чистая установка;
- повторная установка с сохранением данных;
- автоматическое обновление;
- неудачное обновление и откат;
- repair;
- удаление программы;
- backup и реальное восстановление.

### 20.9. Журналы и исправления

После логически завершённой группы действий читается только новый участок журналов. Все действия связываются с видимым результатом и изменением данных.

Найденные проблемы собираются в единый реестр. Потеря данных, смешивание компаний, утечка секрета, падение и опасное удаление останавливают соответствующий сценарий немедленно. Остальные замечания можно собрать и исправлять согласованными пакетами, после чего обязательны новая сборка и повторная проверка затронутых сценариев.

Каждый проверенный этап фиксируется документом и конкретным Git-коммитом. Формулировки `проверено`, `исправлено`, `развёрнуто` и `готово к релизу` используются только при наличии доказательств.

## 21. Когда программу можно назвать готовой

Финальный статус `ГОТОВО К РЕЛИЗУ` разрешён только при выполнении всех условий:

1. исходники находятся в утверждённом Git-коммите;
2. автоматические проверки этого коммита прошли;
3. новый установщик собран именно из этого коммита;
4. хеши установщика и установленной программы сохранены;
5. чистая установка и первый запуск прошли;
6. полный локальный бизнес-цикл прошёл;
7. перенос local-to-server прошёл без потерь и дублей;
8. полный серверный цикл прошёл;
9. два компьютера и несколько пользователей проверены;
10. новый склад и другая компания изолированы;
11. Telegram проверен в живой работе;
12. адресный поиск проверен на утверждённом корпусе;
13. backup и реальное восстановление прошли;
14. автоматическое обновление и откат прошли;
15. все экраны и кнопки проверены визуально и функционально;
16. журналы не содержат секретов;
17. production-серверы обновлены и проверены;
18. нет открытых проблем, способных вызвать потерю данных, смешивание компаний, нарушение прав, неработающую установку, синхронизацию или обновление;
19. оставшиеся неопасные замечания письменно перечислены и отдельно приняты владельцем;
20. подготовлены инструкция, список изменений, канал поддержки и план аварийного отката.

После любого изменения релизного кода создаётся новый кандидат и повторяются все затронутые проверки. Старый установщик нельзя объявлять финальным для нового кода.

## 22. Как вывести программу реальным клиентам

### Что означает пилотная версия

Пилотная версия — это **не урезанная и не визуально упрощённая программа**. Это готовый кандидат в полный релиз, который ограничен только кругом подключённых компаний.

Пилот обязан:

- использовать тот же установщик, интерфейс и набор функций, который планируется передать всем клиентам;
- проходить активацию лицензии, первый запуск и обновление как обычный клиент;
- поддерживать локальное хранение, официальный сервер JustFun и поддерживаемый VPS клиента;
- подключаться ко всем базам и сервисам, входящим в данный релиз: License, PostgreSQL VPS, Telegram Worker/D1, company broker, update catalog, адресный и маршрутный provider;
- пройти local-to-server перенос, несколько складов, пользователей и компьютеров;
- выглядеть как окончательная программа без тестовых заглушек и мёртвых кнопок;
- использовать отдельные pilot tenant/company/warehouse scope, чтобы не смешивать тестовые данные с чужими production-данными;
- иметь backup и проверенный план отката до подключения к каждой реальной базе;
- показывать заметную отметку тестовой среды только при подключении к staging, чтобы сотрудник не перепутал её с production.

Один и тот же собранный файл с тем же SHA-256 должен после успешного production-пилота переводиться в стабильный канал без пересборки. Если код, серверная схема или обязательная конфигурация изменились, создаётся новый кандидат и пилот начинается заново.

### Шаг 1 — закрытая тестовая компания

Полный финальный кандидат устанавливается в отдельной тестовой компании с тестовыми данными. На staging проверяются все поддерживаемые подключения, серверы, миграции, Telegram, адреса, маршруты, обновление и восстановление. Никакие функции будущего стабильного релиза не заменяются заглушками.

### Шаг 2 — ограниченный пилот

Та же полная сборка передаётся небольшой группе согласованных клиентов и подключается к production-инфраструктуре через изолированные области этих компаний. Для каждого фиксируются SHA-256, версии всех серверов, режим хранения, базы/сервисы, состояние переноса и backup. Обновление остальных клиентов ещё не включается.

### Шаг 3 — наблюдение

Проверяются только обезличенные технические показатели: успешность запуска, обновления, миграций, синхронизации, backup и коды ошибок. Содержимое заказов и персональные данные не собираются без отдельного основания и разрешения.

### Шаг 4 — исправление пилотных проблем

Если найдена ошибка, распространение останавливается. Исправление получает новый Git-коммит, сборку, проверки и повторный пилот. Исправленный файл нельзя незаметно подменять под старым номером версии.

### Шаг 5 — стабильный выпуск

После успешного пилота этот же неизменённый кандидат публикуется в стабильном канале. Новые клиенты скачивают его с официальной страницы, а существующие получают проверенное автоматическое обновление. Любое изменение двоичных файлов требует нового номера кандидата и повторного пилота.

### Шаг 6 — постепенное расширение

Версия включается клиентам партиями. Должна сохраняться возможность остановить обновление, временно вернуть предыдущую рабочую версию и уведомить пользователей о подтверждённой проблеме.

### Шаг 7 — сопровождение

Для каждой выпущенной версии сохраняются:

- установщик;
- контрольные суммы;
- Git-коммит;
- серверные версии;
- миграции;
- список изменений;
- известные ограничения;
- инструкция по восстановлению;
- срок поддержки;
- журнал исправлений.
