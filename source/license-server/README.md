# Сервер лицензий и учётных записей JustFun 7.8.3

> Проверено 15.08.2026 через Cloudflare API только для чтения: опубликованный
> `justfun-license-api` совпадал с проверенным состоянием исходников до
> последующего добавления runtime-нормализации старых агрегированных прав.
> Текущая ветка поэтому новее production и ещё не опубликована. Перед deploy
> обязательны миграции, секреты, dry-run и проверка `/health`. Telegram активного
> склада обслуживает отдельный `source/company-telegram-broker`.

Этот исходный код реализует серверный контракт Windows-программы:

- одноразовое создание владельца по ключу;
- вход, обновление сессии и ограниченный автономный доступ;
- одноразовые приглашения сотрудников;
- роли, разрешения, блокировку пользователей и устройств;
- серверный 72-часовой демонстрационный период;
- вход одного пользователя с разрешённых компьютеров;
- единый профиль компании, роли и складские разрешения на всех компьютерах;
- выдачу параметров общего сервера данных после входа;
- совместимый старый маршрут общего Telegram-профиля (новый настольный клиент
  использует отдельный broker с областью `компания + склад`);
- проверку пользовательской сессии сервером данных;
- создание ключей через защищённый административный маршрут;
- журналирование значимых действий и ограничение частоты попыток.

Одноразовость обеспечена ограничением `PRIMARY KEY` таблицы `license_claims`.
Создание пользователя, захват ключа, регистрация устройства и сессии выполняются
одним атомарным пакетом D1: при любом конфликте весь пакет откатывается.

Порядок развёртывания:

1. Создать D1-базу и применить `schema.sql`.
2. Скопировать `wrangler.toml.example` в `wrangler.toml` и указать ID базы.
3. Добавить длинные случайные секреты `JWT_SECRET`, `INTEGRATION_SECRET` и
   `ADMIN_TOKEN`. `INTEGRATION_SECRET` шифрует ключ Telegram Worker в D1 и не
   должен меняться без управляемой повторной настройки интеграции.
4. Выполнить `npm install`, затем развернуть Worker командой `npm run deploy`.
5. Проверить опубликованные маршруты командой
   `node verify-deployment.mjs https://АДРЕС-СЕРВЕРА`.
6. Перед созданием ключа передать административный токен через переменную
   `JUSTFUN_ADMIN_TOKEN`, затем запустить `node create-license.mjs API_ORIGIN COMPANY_NAME [COMPANY_CODE]`.
   Открытый ключ показывается только в ответе на создание и не попадает в список процессов.

`schema.sql` предназначен только для пустой базы и уже содержит актуальную
структуру и отметки всех базовых миграций. Для существующей базы `schema.sql`
повторно не запускается: применяются только отсутствующие файлы из каталога
`migrations` по порядку, после проверки таблицы `schema_migrations`. Миграция
`004-custom-roles.sql` переводит пользователей и приглашения с фиксированного
списка ролей на произвольное название роли; права по-прежнему задаются отдельным
списком разрешений и ограничиваются правами выдающего.

Миграция `005-granular-permissions-audit.sql` добавляет подробности к серверному
журналу изменений доступа. Контракт 4 разделяет планирование, согласование,
комплектацию, выезд, возврат, закрытие рейса, складские движения, цены и
интеграции на независимые разрешения.

Миграция `006-exact-permissions.sql` один раз раскрывает старые укрупнённые права
в точный набор действий. После неё каждое выбранное право действует самостоятельно.

Миграция `007-warehouse-delete-leases.sql` добавляет двухэтапную серверную
блокировку удаления склада. Короткий статус `active` можно атомарно перевести в
долговечный `prepared`. D1-триггеры не дают создать или подготовить блокировку,
если склад уже точно назначен пользователю или действующему приглашению, и не
дают назначить склад, пока `active` не истёк либо пока существует `prepared`.
`prepared` не истекает автоматически и освобождается только явным `release`.
Учитываются только точные права
`jf.warehouse:<id>` и `jf.warehouse-code:<КОД>`; глобальные `*` и
`jf.warehouse:*` намеренно не считаются назначением. Код склада канонически
переводится в верхний регистр и соответствует `/^[A-ZА-ЯЁ0-9]{1,3}$/u`, включая
`СПБ`. Миграция явно переводит старые варианты `спб`/`sPb` в `СПБ`/`SPB`, не
полагаясь на ASCII-only `NOCASE`, а D1-триггеры запрещают снова записать
неканонический вариант. Истёкшие записи `active` переводятся в `expired` перед
новым захватом; `prepared` очистка не затрагивает.

Миграция `008-vps-attestations.sql` добавляет компании только зашифрованное
хранилище HMAC-секрета VPS. Секрет имеет точный формат
`jfvps_[A-Za-z0-9_-]{43,120}`, шифруется AES-GCM с отдельным purpose/context и
не возвращается клиенту, не записывается в audit и не совместим с ciphertext
Telegram-ключа.

Миграция `009-invitation-lifecycle.sql` добавляет отзыв приглашений без удаления
истории. Действующие старые приглашения сохраняются. Отозванный или просроченный
код блокируется D1-триггером даже при одновременной попытке входа. Защищённый
реестр возвращает только срок и состояния `pending`, `used`, `expired`,
`revoked`; исходный код и его хеш никогда не возвращаются. Просмотр требует
`users.read`, а отзыв доступен только владельцу компании и записывается в audit.

## Контракт блокировки удаления склада 3

Маршруты используют обычный access-token пользователя в заголовке
`Authorization: Bearer ...`. Удаление доступно только владельцу либо пользователю
с глобальным правом `*`/`jf.warehouse:*`, у которого также есть
`warehouses.manage`. Право `users.read` не требуется; список, имена и логины
пользователей не возвращаются. `acquire` ограничен по совокупности
`company_id + user_id + IP`; ключ rate-limit хранит только SHA-256 этой области.

- `POST /v1/warehouse-delete-leases/acquire`, JSON
  `{ "warehouse_id": "wh_spb", "warehouse_code": "СПБ" }`.
  Новый захват возвращает
  `{ ok:true, active:true, prepared:false, status:"active", recovered:false,
  lease, remaining_seconds:120, lease_token }`. Если после сбоя владелец или
  администратор с глобальным доступом повторяет точный захват уже подготовленной записи, сервер атомарно меняет
  хеш токена и возвращает ту же запись как
  `{ ..., prepared:true, status:"prepared", recovered:true,
  remaining_seconds:null, lease_token:<новый> }`; старый токен сразу недействителен.
  Новый уполномоченный пользователь становится исполнителем восстановленной операции;
  другой склад, ID или код получает конфликт. В D1 хранится только SHA-256 хеш
  текущего токена.
- `POST /v1/warehouse-delete-leases/prepare`, тот же склад плюс `lease_token`.
  Точный действующий `active` атомарно становится `prepared`; повтор с тем же
  токеном идемпотентен. Ответ:
  `{ ok:true, active:true, prepared:true, status:"prepared", idempotent:<bool>,
  lease, remaining_seconds:null }`. Для `prepared` поля `lease.expires_at` и
  `remaining_seconds` равны `null`, потому что срок больше не освобождает склад.
- `POST /v1/warehouse-delete-leases/verify`, тот же склад плюс `lease_token`.
  Запрос обязан выполнять тот же пользователь той же компании. Успех возвращает
  `{ ok:true, active:true, prepared:<bool>, status:"active"|"prepared", lease,
  remaining_seconds:<integer|null> }`, но не токен. `active` принимается только
  пока он не истёк и имеет не менее 30 секунд; `prepared` принимается независимо
  от старого `expires_at`. Если у `active` осталось меньше 30 секунд, сервер возвращает
  `WAREHOUSE_DELETE_LEASE_REACQUIRE_REQUIRED`: удаление начинать нельзя.
- `POST /v1/warehouse-delete-leases/release`, тот же склад плюс `lease_token`.
  Принимает `active` или `prepared` и переводит запись в `released`. Повтор тем же
  пользователем, складом и токеном после потерянного ответа идемпотентно возвращает
  `{ ok:true, released:true, prepared:false, status:"released",
  idempotent:true, lease }`, не затрагивая другую запись.

Основные ошибки: `400 WAREHOUSE_REQUIRED` или `WAREHOUSE_CODE_REQUIRED`,
`403 ACCESS_BLOCKED`, `409 WAREHOUSE_ASSIGNED` с безопасным объектом
`assigned: { count, users, pending_invitations }`,
`409 WAREHOUSE_DELETE_LEASE_ACTIVE`,
`409 WAREHOUSE_DELETE_LEASE_INVALID_OR_EXPIRED` и
`409 WAREHOUSE_DELETE_LEASE_REACQUIRE_REQUIRED` и `429 TOO_MANY_ATTEMPTS`.
Ошибка назначения во время `active`/`prepared` имеет код
`WAREHOUSE_DELETE_IN_PROGRESS`.

Протокол безопасной саги: после `acquire` VPS сначала выполняет только
неразрушающую проверку склада. Перед отключением Telegram клиент вызывает
`prepare`; с этого момента точные назначения заблокированы до явного `release`,
а сбой восстанавливается повторным `acquire` того же пользователя и цели. Перед
финальным PostgreSQL commit VPS вызывает `verify` и принимает только точную
область со статусом `prepared`. После commit или окончательного rollback клиент
вызывает идемпотентный `release`. Токен хранится только в защищённом хранилище ОС;
его и хеш запрещено помещать в URL, journal, логи и audit. Audit содержит только
компанию, пользователя, склад, действие и безопасный статус.

`/health` и `/v1/health` публикуют
`warehouse_delete_lease_contract: 3`. Перед публикацией Worker применяются
миграции 007, 008 и 009, затем `verify-deployment.mjs` проверяет новые признаки.

Маршрут `PUT /v1/company/data-service` доступен владельцу
и сохраняет адрес общего сервера и обязательный `attestation_secret` один раз
для всей компании. В ответ попадают только публичные параметры сервера; секрет и
его ciphertext не возвращаются. После этого любой разрешённый компьютер получает
те же публичные параметры при обычном входе. Маршрут
`POST /v1/auth/introspect` используется сервером данных: он проверяет активность
компании, пользователя и устройства, а также возвращает роль и разрешённые склады.

Публичные для VPS/Telegram маршруты
`POST /v1/vps-attestations/verify` и
`POST /v1/vps-attestations/release-warehouse-delete` не используют bearer
пользователя. Они принимают только подпись `v1=<64 lowercase hex>` в
`x-justfun-vps-signature`, Unix-время в `x-justfun-vps-timestamp` и nonce в
`x-justfun-vps-nonce`. HMAC-SHA256 охватывает компанию, склад, код, команду,
базовую версию, SHA-256 токена lease (для release — SHA-256 пустой строки),
время и nonce. Допустимое отклонение времени — 90 секунд. `verify` принимает
только точный `prepared` lease с совпавшим токеном. `release-warehouse-delete`
атомарно освобождает последнюю точную `prepared` запись и безопасно повторяется
после потери ответа; новая `active` запись не маскируется старой `released`.
Успешные системные действия попадают в audit без секрета, токена и их хешей.

Миграция `003-company-telegram-service.sql` и маршрут
`PUT /v1/company/telegram-service` сохранены только для совместимости со старыми
клиентами. Они не являются источником истины для версии 7.8.3: актуальный
настольный клиент публикует и читает подключение через
`source/company-telegram-broker`, где ключом области служит пара
`company_id + warehouse_id`. Сервер лицензий участвует только в проверке
сессии, компании, устройства, роли и складских разрешений через
`/v1/auth/introspect`; секрет Telegram в него повторно не записывается.

Секреты, созданные ключи и рабочий `wrangler.toml` в архив не включаются.

## Контракт контекста авторизации 2

Начиная с этого исправления ответы регистрации, входа и обновления сессии
возвращают `auth_context_version: 2` и дублируют `user_id`, `company_id`,
`device_id`, роль и разрешения рядом с объектами `user` и `company`. Те же поля
возвращает `/v1/auth/introspect`. Это устраняет зависимость настольного клиента от
одного представления ответа и позволяет обнаружить противоречие между JSON,
access-token и offline-token.

Маршруты `/health` и `/v1/health` возвращают `auth_contract: 5`.
`verify-deployment.mjs` считает развёртывание неготовым, если опубликован старый
Worker без этого признака. Перед настройкой REG.RU настольная программа всё равно
выполняет онлайн-introspection: именно сервер лицензий подтверждает компанию,
пользователя, компьютер, роль и разрешение `company.update` до открытия окна
SSH-пароля.
